# Tests

```bash
tests/run_tests.sh              # everything
tests/run_tests.sh unit         # Python unit tests only
tests/run_tests.sh js           # report front-end only
tests/run_tests.sh pipeline     # Nextflow stub runs only
```

`.github/workflows/ci.yml` runs the same things on every pull request. Nothing here needs a
container, a reference genome, real reads or a network connection.

## Layout

| Path | What it covers | Needs |
| :--- | :--- | :--- |
| `unit/` | Everything under `bin/`: the consensus decision tree, the QC verdict engine, every parser, the k-mer liftover, the read filter, and the awk and filter expressions the process scripts call | `pytest`, `numpy`, `bcftools` for one class |
| `js/` | The report's hand-written ES5 statistics and pure helpers, plus the integrity of the asset bundle | `node` (>= 18) |
| `pipeline/` | Samplesheet validation, parameter handling, and a full `-stub-run` of the DAG | `nextflow`, Java 17+ |
| `data/` | The fixture cohort, generated by `data/make_test_data.py` | - |

Legs whose tool is not installed skip themselves rather than fail, so a partial local setup still
gets useful signal. The `bcftools` class in `unit/test_vcf_filter_rules.py` is the one place a real
tool is used: the hom/het expressions have to be ones bcftools accepts *and* that select the records
they claim to, which no amount of string comparison can establish.

### What the process scripts contribute

A `script:` block is unreachable from any test: `-stub-run` replaces it and nothing can import it.
So the decisions that used to live inside those blocks are files under `bin/` that the processes
call, and `unit/` covers them like any other code:

| File | Decides |
| :--- | :--- |
| `vcf_filter_rules.py` | What depth, strand support and allele fraction make a call homozygous or heterozygous |
| `format_snps_for_backbone.awk` | Whether a heterozygote survives re-validation, and the depth the consensus divides by |
| `backbone_allpos.awk` | Reference and alternate observations from an mpileup base string, and the coverage call |

## The fixture cohort

`tests/data/` holds a 5 kb reference with three genes and three samples (170 kB in total):

| Sample | Layout | Why it is there |
| :--- | :--- | :--- |
| `SAMPLE_A` | paired-end, two runs | exercises the per-sample merge |
| `SAMPLE_B` | paired-end, one run | the ordinary case |
| `SAMPLE_C` | single-end | the SE branch, which is easy to break unnoticed |

Everything derives from one seed, so `python3 tests/data/make_test_data.py` reproduces the
committed files byte for byte. CI regenerates them and fails on any diff, which is what keeps the
fixtures something anyone can rebuild rather than binary blobs of unknown provenance.

`data/invalid/` holds one deliberately broken samplesheet per failure mode. They are generated by
the same script, because the exact shape of each row decides which error the validator reaches.

## The two test profiles

`-profile test` runs the fixture cohort with BAMpiro's **default** feature set.
`-profile test_full` additionally turns on every optional branch (Kraken, pathotypr typing,
canonical annotation, the coordinate liftover, the virgin consensus), so one run instantiates
every process in the pipeline. `tests/pipeline/test_stub_run.py` asserts exactly that, so an
optional branch cannot quietly fall out of coverage.

```bash
nextflow run main.nf -profile test -stub-run          # ~3 s, 68 tasks
nextflow run main.nf -profile test_full -stub-run     # ~3 s, 84 tasks
```

A stub run proves the **wiring**: that every channel joins, every declared output is produced and
collected, and nothing is starved or duplicated. It proves nothing about the science, which is
what `unit/` is for.

## Testing the report's front-end from Node

The report ships as one ES5 IIFE that `bin/qcreport/render.py` concatenates from `bin/report_assets/js/*.js`
and splices into `shell.html`. `01_prelude.js` opens the IIFE and `14_boot.js` closes it, so no
fragment is a valid script on its own.

`js/harness.mjs` loads the fragments in the order `render.py` itself declares (it parses
`_JS_MODULES` out of the Python, so the two cannot drift), drops the DOM-wiring fragment, and
appends its own epilogue to capture the declarations and close the IIFE. Function declarations
hoist to the top of the IIFE, so every function is reachable regardless of which fragment declared
it, and nothing depends on line numbers.

The statistics are asserted against **SciPy and statsmodels** reference values rather than against
a snapshot of our own output, so the tests catch a regression against an independent
implementation. Current agreement is around 1e-12.

## Both Nextflow parsers

Nextflow 25.10 and later default to a strict parser that rejects statements at the top level of a
script and requires dynamic process directives to be closures. `main.nf` is written to satisfy it:
the samplesheet parsing is a function, every statement lives inside `workflow`, and each dynamic
`publishDir` is a closure. That syntax is also valid for the v1 parser of the minimum supported
24.04.2, so the CI matrix runs both versions and neither needs `NXF_SYNTAX_PARSER`.

If you add script-level code and the run dies with *"Statements cannot be mixed with script
declarations"*, that is the strict parser: move the code into the workflow or into a function.

## Adding a test

- Unit tests import a script by path with `load_script("name")` from `conftest.py`; `bin/` is not
  a package, but `bin/qcreport/` is, and its tests import it normally (`from qcreport import parsers`).
  Note that importing `qc_report` reads `bin/report_assets/`, so it only works in place.
- Anything on disk goes in `tmp_path`. Do not add files to `tests/data/`; if a fixture is worth
  keeping, add it to `make_test_data.py` so it stays reproducible.
- Tests pin **observed** behaviour. When something looks wrong, the test records what the code
  does today, with a comment saying so, and the defect gets fixed in its own change. A red suite
  on `main` teaches everyone to ignore the suite.
- A new process in `modules/` needs a `stub:` block, or the stub run fails.
  `test_stub_run.py::test_there_is_a_stub_block_for_every_process` catches that early.
